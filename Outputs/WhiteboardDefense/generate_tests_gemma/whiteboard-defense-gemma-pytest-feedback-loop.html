1. High-Level Architecture & Mental Model

One-sentence summary: The script sends a source file to a local Gemma model via Ollama, extracts generated test code from the response, writes it to disk, then iteratively runs pytest and re-prompts the model with failure output until all tests pass or the iteration cap is hit.

2. Architectural Decisions & Trade-offs

Decision Why this instead of alternative Accepted trade-off / risk
Local Ollama, not a cloud API (OpenAI / Gemini) Source code never leaves the machine — critical for proprietary / internal Ceph code. Zero per-token cost, no rate-limits during iteration. Speed and quality ceiling bounded by local GPU/CPU. Cold-start latency if model not loaded.
num_ctx = 32 768 (not the model max of 131 072) Comfortable on 30 GB RAM; avoids OOM on typical dev laptops. Commment-documented with escape hatch to 65 536. Very large source files + long pytest output may be silently truncated by the model before num_ctx is even reached.
Pytest output hard-truncated at 8 000 chars Prevents context overflow when a test file produces megabytes of output (e.g., assertion diffs on large data). Keeps repair prompt well inside the 32 K window alongside source + test code. If the critical failure message appears after character 8 000, the model never sees it; repair loop stalls or diverges.
3-case extract_code_block fallback chain Model responses are noisy — truncated fences and unfenced replies both occur. A single strict regex would silently discard large chunks of valid output. Case 3 (no fence) returns raw LLM prose verbatim, which will fail to compile/run but is better than empty string.
Stateless single-turn chat (no conversation history threading) Simplicity; each repair call is self-contained (source + broken tests + output). Avoids context drift over many turns. Model cannot learn intra-session patterns (e.g., "you made the same mistake three iterations ago"). Each fix starts cold.
Late import ollama inside main() Gives a clear, actionable error (pip install ollama) instead of a bare ImportError traceback on startup. Minor: the import is deferred, so IDE static analysis won't see it at module scope.
--no-feedback escape hatch C++ gtest files can't be run by pytest; the loop would always fail. Flag lets users generate-once and compile manually. User must manually run the build and, if desired, paste output back in for a manual re-invocation.
Default system prompt hard-codes C++/gtest/Ceph domain Optimised for the known primary use-case. Script description says "Python" but actual target is C++ Ceph. Misleading docstring says "pytest unit tests for a Python source file"; the real default is C++ gtest. Overriding via --prompt-file is the intended fix, but it requires user awareness.

3. Data Structures, Algorithms & Invariants

Key Data Structures

  • Ollama message list — list[dict] with role / content keys; always exactly 2 elements (system + user). No history accumulation.
  • Ollama options dict — {"num_ctx": 32768, "num_predict": 16384}; only sent on initial generation, not on fix_tests calls (uses model defaults).
  • pytest_output str — result.stdout + result.stderr, bounded to ≤ 8 000 chars before being embedded in the repair prompt.
  • test_code str — mutable binding threaded through the loop; overwritten each iteration; always reflects the last thing written to disk.

Loop Invariants

  • Termination guaranteed: loop is a bounded for i in range(1, max_iterations+1); cannot run forever. Exit conditions are checked in order: passed → EXIT 0, then i == max_iterations → EXIT 1, then repair and continue.
  • Disk state = last model output: write_tests is called before and after every model round-trip; the output file always reflects the most recent generation, even on failure exit.
  • No partial writes: write_tests opens with "w" (truncate) and writes atomically from the caller's perspective; the file is never in a half-written state within a single OS write call.

⚠️ Invariant gap: fix_tests() does not pass num_ctx/num_predict options to client.chat(). Repair calls use Ollama's model defaults, which may differ from the initial generation limits. This can cause shorter repair outputs, increasing the probability of a truncated fence (Case 2).

4. Threat Model & Adversarial Handling

Context: This is a developer-local automation tool. It is not exposed as a service, has no network listener, and requires explicit CLI invocation. The attack surface is the filesystem and the Ollama local daemon.
Model always produces subtly broken tests that never pass but never fully fail
Threat / Actor Vector Current mitigation Residual risk Severity
Malicious source file injects prompt-injection payloads Attacker-controlled .py/.cpp file embedded verbatim in user message None — content is sent raw to the model Model could be manipulated to output harmful shell commands as "tests". Those commands execute when pytest runs the output file. High
Malicious --prompt-file input Attacker-supplied prompt file replaces system guardrails File existence check only (os.path.isfile) Complete control over model persona; could suppress safety instructions entirely. High
Generated test file executes arbitrary OS commands Model produces os.system() / subprocess calls inside test functions; pytest runs them None — no code review gate before run_pytest Full local code execution under the invoking user's privileges. High
Path traversal via --output write_tests calls os.makedirs + open on the raw argument None — no path canonicalization or allowlist Can overwrite arbitrary files if invoked with a crafted path (e.g., --output /etc/cron.d/payload). Requires attacker control of CLI args. Medium
pytest output exfiltrates secrets Test file reads env vars / secrets files; output captured and sent to Ollama daemon 8 000-char truncation limits blast radius Secrets visible in pytest output string sent to local model; model logs may persist them. Medium
Ollama daemon unavailable or returns garbage Network error / model not pulled Unhandled exception propagates to user as traceback Script crashes ungracefully; no retry or user-friendly message. Low
Denial of iteration budget max_iterations cap (default 5), hard loop bound At worst, 5 × model round-trips + 5 × pytest runs. Bounded, not unbounded. Negligible
Critical design gap — no human-in-the-loop before execution:
The generated test code is written to disk and immediately executed by pytest with zero review gate. In a developer-local setting this is a known and accepted risk, but it must be explicit: running this script against untrusted source code is equivalent to running untrusted code on your machine.

Failure Mode Trigger Observed behaviour Blast radius
Source file too large to fit in context source_code len + system prompt + response headroom > num_ctx (32 768 tokens) Ollama silently truncates the input; model generates tests for a partial file. No error raised. Tests cover only the first N lines. Remaining functions untested. Silent data loss.
Model generates non-Python/C++ text (explanation prose) Model ignores "ONLY return code" instruction extract_code_block Case 3: raw prose written to test file. Pytest fails immediately with syntax error. Wastes all max_iterations trying to fix unfixable prose unless the next generation is better.
Feedback loop never converges Structural issue in source (e.g., missing symbols, C++ with no pytest runner) that the model cannot fix Exhausts all iterations. Exits with code 1. Last broken file on disk. User left with partially correct tests; manual triage required.
Truncated fix response (Case 2 extraction) Large test file + fix_tests not setting num_predict → model hits default token limit mid-response Truncated code written to disk; pytest fails with syntax error on next iteration. Model sent a truncated test file to fix again — compounding. Progressive test file corruption over iterations.
pytest not installed run_pytest → subprocess.run([sys.executable, "-m", "pytest", ...]) returncode != 0; stderr says "No module named pytest". Treated as test failure. Model tries to "fix" the test file — forever. All iterations wasted. Script exits 1 after max iterations with misleading output.
Output directory is a file, not a dir --output /some/existing_file/test.py os.makedirs raises NotADirectoryError. Script crashes with traceback. No file written. Clean failure (no partial state).
Critical failure after char 8 000 in pytest output Large test suite; early tests produce verbose output pushing key failure past truncation point Model never sees the actual failure. Repair prompt is misleading. Model may "fix" irrelevant things. Loop stalls; may produce progressively worse tests while appearing to work.
--prompt-file is a binary file User passes a .pdf or image accidentally read_source opens with encoding="utf-8"; raises UnicodeDecodeError. Script crashes. Clean crash before any model call. No partial state.

6. Observability & Triage Playbook

Logging model: All output goes to stdout via print(). Errors go to stderr. No structured logging, no log file. Exit codes: 0 = success, 1 = max iterations exhausted or fatal error.

[prompt]Custom prompt file loaded successfully.
[write]Test file written/updated to disk.

Quick Health Checks Before Running

  • ollama list — confirm gemma4:latest is pulled.
  • ollama ps — confirm a model is loaded (warm start = faster).
  • python -m pytest --version — confirm pytest is on the same Python used by the script.
  • Estimate token count: wc -w source.cpp × 1.3 ≈ tokens. Keep well under 20 000 to leave headroom for response.

Known Workarounds

ProblemWorkaround
Fix responses truncatedAdd options={"num_ctx": _NUM_CTX, "num_predict": _NUM_PREDICT} to the client.chat call inside fix_tests().
Default prompt generates wrong languagePass --prompt-file with a Python/pytest-specific system prompt.
Source too largeSplit source file; run script once per module; or raise _NUM_CTX to 65536 if RAM allows.
Critical failure past 8 000-char truncationTemporarily raise max_output_chars in main(), or pre-filter pytest output to last N lines.
