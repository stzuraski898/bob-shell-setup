2 · Data Structures, Algorithms & Invariants

Top-Level Return Shape

list[
  {
    "object":         str,          # basename without "-intent.md"
    "head_sha":       str,          # 40-char hex (default fallback hard-coded)
    "date":           str,          # free-form string from markdown header
    "commits":        int,
    "source_files":   list[str],    # sorted, deduplicated
    "function_count": int,
    "functions":      list[FunctionDict],
    "totals": {
      "diverged":      int,
      "ungrounded":    int,
      "overcautious":  int,
      "concern":       int,
      "clean":         int,
      "with_concerns": int
    }
  }
]

FunctionDict Shape

{
  "id":           str,          # "{object}_{1-based index}"
  "title":        str,          # heading text stripped of ` * backtick/asterisk
  "status":       str,          # "CLEAN" | "DIVERGED" | "UNGROUNDED" | "OVERCAUTIOUS" | "CONCERN"
  "counts": {
    "diverged":     int,        # DIVERGED + DEFECT + HAZARD tags + **Divergence:** field
    "ungrounded":   int,        # UNGROUNDED tags
    "overcautious": int,        # OVERCAUTIOUS tags
    "concern":      int         # CONCERN + GAP + RISK + MISSING tags
  },
  "locs":         list[str],    # e.g. ["src/mgr/Foo.cc:123"]  (first 300 chars only)
  "raw_markdown": str           # verbatim markdown slice for that section
}

Status Severity Precedence (strict total order)

PriorityStatusTrigger TagsColour
1 (highest)DIVERGEDDIVERGED, DEFECT, HAZARD or **Divergence:** <word containing DIVERGE>Red
2UNGROUNDEDUNGROUNDEDYellow
3OVERCAUTIOUSOVERCAUTIOUSPurple
4CONCERNCONCERN, GAP, RISK, MISSINGOrange
5 (lowest)CLEANNo tags matchedGreen
Invariant: Status is assigned by the worst single tag present. Counts accumulate independently (a function with 3 DIVERGED + 2 UNGROUNDED tags gets status=DIVERGED, but counts.ungrounded=2 is still recorded — not zeroed out).

Heading-Level Selection Algorithm

chosen = h2_candidates  if  len(h2) >= len(h3)  AND  len(h2) > 0
       = h3_candidates  otherwise
       = all_candidates if both sets empty
Rationale: some intent files use ## for functions, others use ### under a class-level ## header. The algorithm picks whichever level has more candidates (favouring H2 on a tie). This is heuristic-based, not schema-enforced.

Candidate Tuple Layout

(level: int, line_idx: int, raw_line: str, clean_title: str)
  • level — 2 or 3 (heading depth)
  • line_idx — 0-based index into lines[]
  • raw_line — original markdown line (unused after candidate list built)
  • clean_title — markdown formatting stripped via re.sub(r"[`*]", "", title)

Non-Function Header Exclusion Table

A set[str] of 44 lowercase sentinel values guards H2 exclusion. H3 exclusion uses an inline list of 23 prefixes. Matching logic:

# H2 check (non_func_titles set):
clean_lower.startswith(x) OR clean_lower == x

# Additional H2 guard (positional prefixes):
startswith("class:") | startswith("1.") | ... | startswith("5.")

# H3 check (inline list):
clean_lower.startswith(x) OR clean_lower == x
Known gap: The H2 and H3 exclusion lists are maintained separately and have grown organically. A new intent template section name that isn't in either list will silently be treated as a function.

commits.txt Fallback

path: Outputs/Object History/v4/{obj}/commits.txt
trigger: commits_count == 0 after regex
count: non-empty lines (strip + bool)

Note: comment lines (# ...) count toward total because there is no startswith("#") guard in the fallback counter — unlike the functions.txt reader which does skip comment lines.

3 · Architectural Decisions & Trade-offs

DecisionWhat Was DoneWhy Not Y?Consequence
Line-split then index text.split("\n") once; all heading detection and slicing operates on lines[] Streaming / regex on raw string would lose line numbers needed for slice boundaries Entire file in memory; fine for ~500–2000 line intent docs
Heuristic level selection (H2 vs H3) Choose whichever heading level has more candidates Fixed schema would break existing intent files that use either convention Misclassification if a file has exactly equal H2/H3 counts (H2 wins on tie)
Bold **TAG** regex scanning re.findall(r"\*\*(TAG)\*\*", fn_text) YAML front-matter or structured fields would require a different authoring format Tags must be exactly **WORD**; partial bold or lower-case are silently missed
Worst-severity wins for status First non-zero count in precedence order sets status Average / aggregate scoring would obscure single critical findings A function with 10 CLEAN + 1 DIVERGED is labelled DIVERGED — conservative, intentional
Hard-coded fallback SHA head_sha = "8681fa6e..." as default before regex Leaving it empty/None risks downstream consumers breaking on missing SHA Silently produces wrong SHA if regex fails; no warning emitted
LOC extraction limited to fn_text[:300] Only the first 300 chars of a section are scanned for source locations Full-text scan would return every inline code citation, not just the canonical "Introduced at" metadata header LOC refs appearing after the preamble block are missed
Raw markdown stored in each function record "raw_markdown": fn_text in every FunctionDict Keeping only parsed fields saves memory/disk but loses rendering capability for downstream HTML generators parsed_intents.json can be large; each intent file's full text is duplicated as per-section slices
No schema validation on input markdown All parsing is best-effort; missing metadata fields produce empty strings / 0 Strict validation would require a formal intent-file schema, which doesn't exist yet Malformed or unexpected intent formats degrade silently
Re-derive object name from filename os.path.basename(f).replace("-intent.md", "") Could embed a canonical name in the markdown header; would require parsing coordination Filename must match the expected NAME-intent.md convention exactly

4 · Threat Model & Adversarial Handling

Actor / InputAttack / Unexpected BehaviourCurrent HandlingRisk Level
Malicious markdown author Inject a heading that looks like a function but isn't (e.g. ## Summary) — missing from exclusion table Treated as a function; gets status=CLEAN, inflates function counts MEDIUM
Malicious markdown author Insert **DIVERGED** inside a code fence or quote block to artificially poison a CLEAN function Regex has no code-fence / blockquote awareness; tag is counted regardless of context MEDIUM
Crafted file path A file named ../../etc/passwd-intent.md placed in the intents directory glob restricts to Outputs/Intents/; os.path.basename strips path. Reads only within glob pattern. No write back to that path. LOW
Huge intent file Multi-MB markdown file (pathological doc) Entire file read into memory at once; text.split("\n") produces a large list. No size guard. Could cause OOM on very large files. MEDIUM
Corrupt functions.txt Lines with no | separator, or parts[1] missing len(parts) >= 2 guard skips malformed lines safely LOW
commits.txt comment injection Many # comment lines inflate commit count (no skip guard in fallback) Comment lines ARE counted in the fallback path (bug). Non-empty lines including # lines count. MEDIUM
Duplicate heading titles Two functions with identical ## FunctionName headings in one file Both become separate FunctionDict entries; id is index-based so they differ. No dedup or warning. INFO
Unicode / BOM in markdown Non-ASCII characters in function titles or invisible BOM at file start Files opened with encoding="utf-8". BOM would appear in first heading title; no explicit strip. functions.txt opened without explicit encoding (platform default). MEDIUM
JSON output path collision Another process writes parsed_intents.json concurrently No locking; plain open("parsed_intents.json", "w"). Last writer wins. Not a concern in single-process batch use. LOW (batch tool)

Triage: Unexpected Function Count

  • Run python parse_data.py, compare Funcs: against manual grep -c "^## " file.md
  • If counts diverge: check whether new section names need adding to non_func_titles or H3 exclusion list
  • Inspect chosen_candidates by adding a print for the object in question

Triage: Wrong SHA / Date / Commits

  • Grep the intent file header manually: grep -i "HEAD SHA\|Corpus HEAD" file.md
  • If the keyword variant doesn't match the regex, update the alternation in re.search(r"\b(?:HEAD SHA|Corpus HEAD)[:\s*\`]+...")
  • Commits fallback: check if commits.txt exists under Outputs/Object History/v4/{obj}/; verify comment lines aren't dominating the count

Triage: Status Wrong (DIVERGED when should be CLEAN)

  • Search the raw section: grep -n "\*\*DIVERGED\*\*\|\*\*DEFECT\*\*\|\*\*HAZARD\*\*" file.md
  • Check if matching tag is inside a code fence (```) — if so, this is the known tag-in-fence bug
  • Check the **Divergence:** field: grep -i "Divergence:" file.md

Triage: Missing Source Files

  • Check Outputs/Object History/v4/{obj}/functions.txt exists and has pipe-delimited lines
  • Verify format: qualified_name | file.cc:linenum

Bottom line for whiteboard: parse_data.py is a single-pass, best-effort markdown ETL tool. It globs intent files, applies layered heuristics (exclusion tables → level selection → bold-tag regex) to extract per-function status records, and serialises to JSON. Its correctness depends entirely on intent files following the expected markdown conventions. Failures are always silent — wrong data, never crashes.
