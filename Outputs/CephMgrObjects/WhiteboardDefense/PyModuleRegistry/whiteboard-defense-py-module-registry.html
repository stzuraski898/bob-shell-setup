1High-Level Architecture & Mental Model

PyModuleRegistry is the single owner of the CPython interpreter lifecycle and every PyModule object in the mgr daemon. It acts as a switchboard between the mgr's two operational personas — standby and active — and the set of Python modules discovered on disk.

2Architectural Decisions & Trade-offs

Decision: Why X? Alternative (Y) Rationale & SHA
Modules discovered from disk (probe_modules) not from MgrMap.modules Only load modules the mon says are enabled All modules must be loaded early so their command definitions can be registered before a MgrMap arrives. Commands exposed to the CLI are static metadata. 6a8da7ca (2017-11-16)
init() decoupled from MgrMap — takes no map argument Pass the map to init() Registry must start Python interpreter before the mon connection is up. init() is called at daemon start; the map arrives later via handle_mgr_map(). 810369b0 (2018-02-05)
Failed modules are kept in modules map Remove failed modules from the map The error must be reportable via get_health_checks(). Removing failed modules would silently drop them from health reporting. 7c80548d (2018-03-15)
active_start() gates on is_loaded(), not get_can_run() Skip modules that report can_run=false Modules must be allowed to start even when can_run=false so they can self-report their dependency problems via their own health checks. cf5ef59b (2018-04-23)
standby_start() gates on is_enabled() && get_can_run() Start all loaded modules in standby too Standby modules are optional/lightweight. Only those that can actually run and have a standby class are started. Always-on modules that fail this check are cluster-log-reported. cf292dfa (2018-07-16)
Modules started in a Finisher thread, not inline Start modules synchronously in active_start() Module start can call back into the mgr OSD map or KV store, creating lock-cycle deadlocks if done inline. Finisher decouples startup from the dispatch thread. f22347db (2019-01-24)
PyConfig / Py_InitializeFromConfig instead of deprecated Py_SetProgramName + Py_InitializeEx Continue using the deprecated pre-3.12 init API Python 3.12 removed the old API. PyConfig also gives explicit control over signal handlers, C stdio, and argv parsing. 4cf9b36c (2024-02-03)
PYTHONPATH merged via PyConfig.pythonpath_env before interpreter init Manually call sys.path.insert() post-init Setting pythonpath_env before Py_InitializeFromConfig means the interpreter sees the correct path from the first import. Post-init manipulation is fragile and order-dependent. 51a5774a (2024-02-03)
ceph_logger only registered when daemonize=true Always register ceph_logger In unit-test / non-daemonized contexts, the logger conflicts with Python's own stdout. 410ce76f (2018-02-08)
std::filesystem::directory_iterator instead of POSIX opendir Keep POSIX opendir Modern C++17 cross-platform path handling; eliminates manual closedir RAII. However, it silently dropped the original error-tolerant behaviour (see §5). 40d06ce6 (2020-04-30)
force_disabled_modules explicitly checked and skipped in active_start() Rely on the enabled flag alone Operator can force-disable an always-on module at runtime via the mon. The force-disable path is orthogonal to the normal enabled/disabled path and needs an explicit bypass. 9962772 (2024-07-19)
No Py_Finalize() on shutdown — rely on process exit Clean Python shutdown via Py_Finalize() Py_Finalize() with extension modules is dangerous (deadlocks, crashes on cleanup). The removed shutdown() function embodied this rationale; after dd9f9e26 (2023-11-02) the mgr just exits on SIGTERM.
Config values are not logged (key only) Log full key=value for debugging Module config can store cluster credentials and user secrets. 19000fad (2020-12-03) intentionally suppressed value logging with a commented-out line as a visible reminder.
Two separate locks: outer lock and module_config.lock Single lock for all state handle_config() can be called concurrently while active_start() holds the outer lock. Fine-grained locking avoids deadlock on the config path. 3193d40d (2018-02-16)

3Data Structures, Algorithms & Invariants

Structure Type Why This Type Key Invariant
modules map<string, PyModuleRef> Keyed by module name; stable iteration order; lookup by name is the dominant access pattern Populated once in init(), never cleared. Contains all discovered modules, including load failures. Never modified after init().
standby_modules unique_ptr<StandbyPyModules> Exclusive ownership; null = not running. Avoids shared ownership complexity. Non-null only between standby_start() and the next active_start(). Never non-null simultaneously with active_modules.
active_modules unique_ptr<ActivePyModules> Same rationale. Null-check is cheap and unambiguous. Non-null only after active_start(). All callthrough functions with ceph_assert(active_modules) enforce this (ab23c506).
module_config.config map<string, string> Simple KV store; config keys are arbitrary strings. Map provides O(log n) lookup and ordered iteration. Protected exclusively by module_config.lock (not outer lock). Empty value = deletion. 3193d40d
clients multimap<string, entity_addrvec_t> A module can register multiple client addresses (e.g., CephFS mounts). Multimap allows one name → many addrs naturally. Protected by outer lock. unregister_client exits on first match (12375a4c fixed prior endless-loop bug).
probe_modules() result vector<string> Changed from set<string> (7d2964bf). Vector is cheaper for a one-shot iteration that never needs set semantics. Used only during init(); discarded afterward.
pMainThreadState PyThreadState * CPython requires saving the main thread state to re-acquire the GIL from C threads. This pointer is the re-entry point. Set once in init(), never reset. ceph_assert(pMainThreadState != nullptr) after PyEval_SaveThread() (ab23c506).

4Threat Model & Adversarial Handling

Threat / Adversarial Input What Happens Hardness
Malicious module on disk — a Python file in mgr_module_path crafted to execute arbitrary code on import probe_modules() will find it; PyModule::load() will import it, executing the module-level code. The Python interpreter runs as the mgr daemon's OS user. NO PROTECTION — the mgr daemon inherently trusts mgr_module_path. Mitigation is filesystem-level permissions on that directory.
Module registers a command with a clashing name get_py_commands() collects all commands from all modules and returns them all. Duplicate resolution happens upstream in MonClient command dispatch, not in the registry. LOW PROTECTION — no deduplication or conflict detection in the registry.
Operator issues handle_command before active modules are running Returns -EAGAIN immediately with an explanatory message. 834bc279 SAFE
Module floods register_client with many addresses Each call takes lock and inserts into the clients multimap. No cap on entries. A misbehaving module could grow the multimap unboundedly. UNBOUNDED — no size limit on clients.
Race: handle_command called during active_start() shutdown handle_command reads active_modules without holding lock. TOCTOU exists: pointer could be nulled by active_start's standby-shutdown path between the null-check and the dereference. TOCTOU — UNGROUNDED (see §5). In practice, standby→active transition is serialised by mgr's dispatch thread.
Attacker can enumerate module config keys handle_config logs the key (not value) at dout(10). Config keys themselves may be sensitive (e.g., encode module names + option paths). LOW RISK — dout(10) not visible without debug logging enabled.
should_notify(name) called with unknown module name modules.at(name) throws std::out_of_range, which propagates uncaught unless the caller handles it. THROW — UNGROUNDED — caller must ensure name is in the map. Inconsistent with get_module() which uses safe find().
mgr_module_path does not exist probe_modules() throws std::filesystem::filesystem_error (uncaught). Daemon crashes at startup. CRASH — UNGROUNDED — original POSIX opendir silently returned empty. See §5.
Module disabled in mgr_disabled_modules but still present on disk Filtered by probe_modules() before even being loaded. Module never enters the modules map. 067adbf9 SAFE
Always-on module force-disabled by operator via mon Set as force_disabled in MgrMap. active_start() explicitly skips it (9962772). Not reported as an error in health checks. SAFE
Python module hangs during serve() ThreadMonitor (started after GIL drop, 95a90f7d) detects hung threads and reports them. Shutdown relies on module co-operation; a truly hung module blocks daemon shutdown. PARTIAL — detection exists; forced kill is process-level only.

5Failure Modes, Edge Cases & Blast Radius

🔴 Fatal (daemon abort)

  • PyConfig_SetString / Py_InitializeFromConfig fails → ceph_assertf aborts. 4cf9b36c
  • pMainThreadState == nullptr after PyEval_SaveThread() → ceph_assert. ab23c506
  • active_start() / standby_start() called with preconditions violated → ceph_assert. ab23c506
  • PyImport_ImportModule("site") returns null in get_site_packages() → ceph_assert. ab23c506
  • mgr_module_path missing/unreadable → std::filesystem::filesystem_error thrown uncaught from probe_modules().

🟡 Non-Fatal (degraded service)

  • mod->load() fails → module inserted with !is_loaded(); reported via MGR_MODULE_ERROR health check. 7c80548d
  • No modules found at all → cluster log error only, daemon continues. 67a47951
  • Always-on module won't run in standby → cluster log error, daemon continues. cf292dfa
  • Module stuck in pending_modules past expiry → MGR_MODULE_ERROR health check. bf25a08c
  • Active module fails at runtime (non-always-on) → surfaced via MGR_MODULE_ERROR; other modules unaffected. d9a47181

Bottom line: PyModuleRegistry is the sole gatekeeper for Python in the mgr. Its design trades strict safety (no dynamic load/unload, failed modules kept in map, module start in finisher threads) for observability and fault isolation. The main production risks are: (1) a bad mgr_module_path crashes the daemon instead of logging an error, and (2) the check_all_modules_started / get_pending_modules callthroughs lack the ceph_assert(active_modules) guard that all other callthroughs enforce.
