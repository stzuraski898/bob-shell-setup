Whiteboard Defense: MgrMapCache

Architectural analysis, threat modeling, and design justification for Ceph's thread-safe manager map cache.

Class: MgrMapCache<Value> Specialization: MgrMapCache<PyObject*> Successor of: TTLCache Establishing Commit: 403340bcf8c2122afff708519f176baa6b646fc1 Subsystem: ceph-mgr

1. High-Level Architecture & Mental Model

MgrMapCache is a high-performance, generic LFU (Least Frequently Used) cache with a vital full template specialization for PyObject*. It is designed to cache heavy, frequently requested manager API results (like cluster state maps) and expose them safely to Python-based manager modules.

By migrating from the legacy time-based TTLCache to an LFU policy under commit 403340bcf8c2122afff708519f176baa6b646fc1, the cache guarantees optimal hit rates for data that is requested in tight python-module loops, while avoiding the dynamic latency spikes and safety hazards of time-to-live expirations.

2. Architectural Decisions & Trade-offs

The table below explains why specific design patterns and abstractions were selected over traditional alternatives, grounded in Ceph manager architectural constraints.

Why did you do X... ...Instead of Y? Architectural Justification & Grounding
LFU (Least Frequently Used) Eviction Time-Based Cache (TTL) or standard LRU Predecessor TTLCache caused map evictions during intensive, repetitive Python processing cycles, forcing constant serialization/re-reads of massive OSD and PG maps. LFU keeps hot objects cached regardless of age. Eviction occurs only when capacity is exhausted, targeted at the absolute least frequently utilized maps.
Heterogeneous Map Lookups (StringViewHash) Default std::unordered_map lookup with string key Standard lookups require constructing a temporary std::string, allocating heap memory on every query. Defining StringViewHash and utilizing std::equal_to<> with using is_transparent = void; enables lock-time lookups using non-allocating std::string_view. String keys are allocated only during new map insertions.
GIL-Safe Deferred Decrefs (Py_AddPendingCall) Direct C++ thread Py_DECREF invocations Cache invalidation, replacement, or evictions can occur on background C++ worker threads. Releasing a Python object's memory via Py_DECREF requires holding the Global Interpreter Lock (GIL). We schedule cleanups on Python’s own main thread using Py_AddPendingCall, preventing fatal segmentation faults and race-induced reference count corruption.
Shared/Exclusive Locks (std::shared_mutex) Standard std::mutex or atomic pointer swapping Ceph's manager undergoes massive concurrent read volumes from multiple active modules, but writes are bursty (epoch increments). std::shared_mutex supports concurrent readers under std::shared_lock, preventing reader-thread starvation while protecting insertions under std::unique_lock.
Full Template Specialization Polymorphic base pointers or runtime type checking Provides zero-overhead, compile-time safety. Specializing MgrMapCache<PyObject*> allows compile-time deletion of standard helper methods like try_get (which does not manage reference counts safely) and forces programmers to use GIL-safe, INCREF-guaranteed access paths.

3. Data Structures, Algorithms & Invariants

Core Containers & Structures

  • The Hash Map: std::unordered_map<std::string, Entry, StringViewHash, std::equal_to<>>. Key features: Heterogeneous transparent search, lazy allocation of keys on insertion only.
  • The Entry Structure: Holds the stored value and a mutable std::atomic<size_t> hits. Marked mutable so hits can be updated under a std::shared_lock read operation.
  • Allowed Cache Keys: Restricted to an immutable allow-list (mgr_cache_keys) defined in MgrMapCache.cc: "osd_map", "pg_dump", "pg_stats", "mon_status", "mgr_map", "osd_metadata", "mds_metadata", "config".

Eviction & Watermark Invariants

  • Capacity Boundary: Initialized with a maximum capacity (defaulting to UINT16_MAX).
  • LFU Eviction Selection: When capacity is reached, the entry with the minimum hit count is chosen using std::min_element. If multiple elements have identical minimum hit counts, the tie-breaker is determined by hash-bucket iteration order (non-deterministic but fast).
  • The Trim Watermark: Controlled dynamically via mgr_map_cache_enabled. Whenever flipped to disabled:
    1. The config observer (md_config_obs_t) triggers set_enabled(false).
    2. Virtual dispatch invokes clear().
    3. The PyObject* specialization immediately drains elements and releases references safely under Python's GIL.
Critical Invariant: Atomic Py_INCREF Under Shared Lock
In MgrMapCache<PyObject*>::get, the Python reference count is incremented (Py_INCREF(o)) inside the shared-lock critical section. This guarantees no racing C++ thread can call erase/extract, drop the reference count to zero, and free the underlying object before the reading thread successfully claims ownership.

4. Threat Model & Adversarial Handling

The manager cache acts as the boundary between untrusted/complex Python module execution and high-performance, critical C++ Ceph daemons. It must defend against unexpected behaviors from both environments.

Adversarial Scenario Impact if Unmitigated Mitigation & Defense Mechanism
Python module executes write/read without GIL Severe memory corruption, interpreter thread-state desynchronization, core dumps. Both get and insert specialization methods strictly check PyGILState_Check(). If called without holding the Python GIL, they immediately abort and return nullptr or skip execution.
Memory leaks via disabled races A thread increments Py_INCREF, but before it can insert the item, the cache is disabled, leading to a leaked reference. The write lock rechecks the atomic enabled state inside the critical section. If disabled, insert returns {false}, and the specialization instantly runs an undo-decrement (Py_DECREF), preserving the reference balance.
Adversarial key flooding / Cache stuffing A compromised/buggy module fills the cache with arbitrary keys, leading to OOM or evicting hot system-critical maps. Strict key filtering using is_cacheable(key). Only maps included in the static allow-list are cacheable. Arbitrary keys are immediately ignored.
Concurrent Delete & Read Race A reading thread finds a pointer, but before it increments the refcount, a background writer evicts it, causing a use-after-free. The reading thread holds a std::shared_lock over the map, and performs Py_INCREF prior to releasing the lock. The writer cannot execute map erasure (which requires a std::unique_lock) until the read lock is freed, eliminating the race window.

5. Failure Modes, Edge Cases & Blast Radius

Knowing where software fails is as critical as knowing how it works. These are the explicit bottlenecks, failure boundaries, and minor design compromises present in the current architecture.

Failure Mode 1: Ignoring Py_AddPendingCall Failures in erase
When an item is explicitly erased from the Python specialization cache via erase(key), the code calls Py_AddPendingCall to schedule the Py_DECREF callback. However, the return value of Py_AddPendingCall is ignored (unlike insert which falls back to PyGILState_Ensure if it fails). If Python is shutting down or the pending-call queue is exhausted, the decref callback is lost, causing a silent leak of the cached PyObject*.
Failure Mode 2: Lock Contention Under Severe Module Over-polling
Although reads utilize a shared lock, highly multithreaded Python modules running in parallel can still cause lock contention on std::shared_mutex m. Because get must record hit statistics (calling mark_hit() and updating performance counters), write-side tasks (such as map invalidation or cluster status updates) might experience slight latency spikes while waiting for readers to release the shared lock.

Boundary Conditions & Edge Cases

  • Eviction Tie Handling: When multiple entries have been read 0 times (e.g. freshly inserted entries), std::min_element selects the first match in iteration order. Because of hash map bucketing, eviction is non-deterministic but guarantees O(1) space preservation.
  • Wrapper Copy Behavior: The generic wrapper insert(k, v) discards the internal ownership result (InsertRes). While fine for POD types, this makes tracking eviction in generic classes difficult outside the specialization.
  • Observer Lifetime: The cache registers itself with g_conf().add_observer(this) on construction and must unregister during destruction to avoid trailing pointer dereferences in the configuration proxy.

6. Observability & Triage Playbook

When troubleshooting Ceph manager performance or suspected leaks, follow this precise handbook.

Performance Counters & Core KPIs

The cache exposes critical performance metrics to Ceph's administration daemon. Check these indicators using: 

ceph daemon mgr.<id> perf dump
  • l_mgr_cache_hit: Snapshot of total cache reads served successfully from RAM.
  • l_mgr_cache_miss: Snapshot of cache misses, indicating either first-time loads or items evicted due to size.

Verifying & Triaging Map Cache Leaks

  1. Enable Verbose Debug Logs: Set log level 20 for the manager subsystem to output granular cache trace information (logs insertion counts, reference balance, cache clearances, and hits/misses): 
    ceph config set mgr debug_mgr 20
  2. Analyze Reference Balance: Look for lines matching api cache insert key: <key> py count: <refcount>. If the refcount for static keys keeps growing without bound while no new modules are loaded, it indicates reference leaks outside the cache boundaries.
  3. The "Nuclear Option" (Dynamic Invalidation): If you suspect cache corruption or stale map problems: 
    ceph config set mgr mgr_map_cache_enabled false
    This config change is caught by the observer, triggers immediate virtual clearing, ensures safe GIL state acquisition, and decrements reference counts of all stored PyObjects immediately. Re-enabling starts the cache fresh with zero state.
