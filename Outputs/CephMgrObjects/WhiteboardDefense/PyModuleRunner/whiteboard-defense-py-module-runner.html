Whiteboard Defense: PyModuleRunner

src/mgr/PyModuleRunner.{cc,h}  ·  Author: John Spray (RedHat, 2017)  ·  Last significant change: Nitzan Mordechai, Dec 2024

1. High-Level Architecture & Mental Model

PyModuleRunner is the C++ harness that bridges a native OS thread to a Python interpreter thread state so that a MgrModule subclass can call its long-running serve() loop. It is a base class — never instantiated directly. Two concrete subclasses exist: ActivePyModule (active mgr) and what was formerly StandbyPyModule.

Object Relationships

  MgrModule (Python)
       │  inherits
       ▼
  pClassInstance  ◄──── PyModuleRunner (C++ base, abstract)
       │                      │
       │                      ├── py_module (PyModuleRef / shared_ptr<PyModule>)
       │                      │       └── pMyThreadState (SafeThreadState)
       │                      │
       │                      ├── PyModuleRunnerThread  (extends Thread)
       │                      │       └── calls serve() on entry
       │                      │
       │                      └── ThreadMonitor* (optional, perf/CPU)
       │
  ActivePyModule (concrete)
       └── finisher (per-module Finisher for command dispatch)

Lifecycle / State Machine

  CONSTRUCTED
      │
      │  thread.create()  (caller's responsibility — not done inside this class)
      ▼
  THREAD ENTRY  ── PyModuleRunnerThread::entry()
      │               stores runner_tid (atomic release)
      │               calls serve()
      ▼
  SERVING  ── GIL acquired (new_thread=true)
      │         perfcounter "alive" → 1
      │         PyObject_CallMethod(pClassInstance, "serve")
      │
      ├── [normal return] → perfcounter "alive" → 0 → return 0
      │
      └── [exception / NULL return]
              peek_pyerror()  → clog->error()
              handle_pyerror(crash_dump=true)  → derr
              py_module->fail(exc_msg)
              return -EINVAL

  SHUTDOWN  ── shutdown() called from different thread
      │         GIL acquired (new_thread=true)
      │         PyObject_CallMethod(pClassInstance, "shutdown")
      │         perfcounter "alive" → 0
      └──       dead = true

  DESTROYED  ── ~PyModuleRunner()
                  GIL acquired (new_thread=true)
                  Py_XDECREF(pClassInstance)

GIL Acquire Points

Sitenew_thread=Why
serve()true Called from native OS thread (PyModuleRunnerThread) not created by Python — must allocate a fresh PyThreadState via PyThreadState_New(interp)
shutdown()true Same reason — mgr C++ thread, not a Python-born thread. Fixed in 29193a47e6c (SafeThreadState update).
~PyModuleRunner()true Destructor runs in C++ caller's thread — must create a new PyThreadState to safely call Py_XDECREF.
Key invariant: new_thread=true causes Gil to call PyThreadState_New(interp) + PyEval_RestoreThread(), and its destructor calls PyThreadState_Clear() + PyEval_SaveThread() + PyThreadState_Delete(). The thread state is fully scoped to each call site — no state leaks across invocations.

2. Architectural Decisions & Trade-offs

DecisionWhy this, not Y?Commit
Base class, not standalone object
ActivePyModule : public PyModuleRunner 		Active and standby modules both need the same serve/shutdown/GIL pattern. Before df8797320be, ActivePyModule and StandbyPyModule duplicated this logic. Extraction into a base class eliminates duplication. df8797320be (2017-10-06)
SafeThreadState instead of raw PyThreadState* A raw pointer cannot assert that GIL restore happens from the correct POSIX thread. SafeThreadState stores pthread_t and checks it in Gil(new_thread=false) to prevent silent cross-thread GIL corruption. 625e1b5cfb9 (2017-10-03)
new_thread=true for all call sites here All three call sites (serve, shutdown, destructor) run on native OS threads. Using false would cause Gil to assert pthread_self() == pThreadState.thread and abort. The comment in serve() explicitly documents this. 29193a47e6c
thread_name = py_module->get_name().substr(0, 15) Linux pthread_setname_np caps thread names at 15 characters (+1 NUL). Silently truncating is the correct approach since the OS will reject longer names with ERANGE. 13bcddea23f
Two-phase error reporting: peek_pyerror() then handle_pyerror() Cluster log (clog) needs a short, human-readable message without a full traceback (noise in a distributed log). The local daemon log (derr) gets the full backtrace. peek_pyerror reads the error without consuming it; handle_pyerror drains and formats it. Added in f4763c32fa8, refined in 719d5e1836c. f4763c32fa8, 719d5e1836c
Crash dump generation for serve() exceptions An exception escaping serve() indicates an unhandled fault in a system-level daemon component. Generating a crash dump (with handle_pyerror(true, ...)) makes these visible in cluster health and correlates module exceptions with daemon crash records. Traceback intentionally omits the exception value to avoid leaking identifying information. 719d5e1836c
dead flag set only after shutdown completes Tracker #42744: before this fix, a finisher callback could invoke notify() on a module whose destructor had already run. The dead flag (checked by is_dead()) lets callers gate on completion before dispatching further. 40c4b9ac9d8
Per-module perf counters (l_pym_alive, CPU, RSS) Previous observability required manual instrumentation inside each Python module. Counters at the C++ harness layer are module-agnostic: every module gets them for free without modifying Python code. "Alive" counter uses set(0/1) rather than increment/decrement to be idempotent. 95a90f7da8a
runner_tid stored atomically with memory_order_release TID is written at thread entry (before any work), read later by ThreadMonitor. Release semantics ensure the write is visible before any subsequent reads in other threads. A non-atomic store could be observed as zero by a racing reader. 95a90f7da8a

3. Data Structures, Algorithms & Invariants

Key Fields

FieldTypeInvariant
py_module PyModuleRef (shared_ptr) Never null after construction. Owns pMyThreadState and perf counters. Outlives the runner.
pClassInstance PyObject* Set by subclass before calling serve(). Protected by ceph_assert(pClassInstance != nullptr) at every call site.
dead bool (private) Set to true only in shutdown(), after the Python call completes. Read via is_dead().
thread (PyModuleRunnerThread) extends Thread (pthread wrapper) Created in constructor, must be explicitly create()-d and join()-ed by the owning ActivePyModule. Not self-managing.
runner_tid std::atomic<pid_t> Zero until PyModuleRunnerThread::entry() stores the native TID. ThreadMonitor reads this after thread start.
thread_name std::string (≤ 15 chars) Truncated at construction. Used by ActivePyModule's finisher thread name too.
pMyThreadState (on PyModule) SafeThreadState Carries PyThreadState* + the POSIX thread that owns it. Validated on every non-new-thread GIL acquisition.

No Non-Trivial Algorithms

The class contains no sorting, searching, or complex state machines. Its value is entirely in the correct sequencing of Python C API calls around a thread boundary. The only algorithmic subtlety is the GIL acquire/release protocol in Gil.

4. Threat Model & Adversarial Handling

ScenarioImpactMitigation
HIGH Python module raises unhandled exception from serve() Module stops running; cluster feature (e.g., orchestrator, balancer) goes dark. Caught by NULL-return check. Emits to cluster log (clog->error). Generates a crash dump with exception type + traceback. Calls py_module->fail() to mark the module failed in MgrMap. No mgr process crash. Returns -EINVAL.
HIGH Module serve() never returns (infinite loop / deadlock) Thread blocked forever; module resources (GIL slot, memory) leaked. ThreadMonitor tracks CPU usage per runner_tid. No hard kill is implemented — detection is observational only. Operator intervention required.
MED Module shutdown() raises exception Shutdown sequence stalls or leaves Python state dirty. Error is logged to derr with full traceback. dead = true is set unconditionally regardless — shutdown always completes from C++ perspective.
MED Notify/finisher callback races module destruction (tracker #42744) Use-after-free / call on destructed object. dead flag checked before dispatch. Fix: 40c4b9ac9d8.
MED GIL acquired on wrong thread (new_thread=false from foreign thread) Python interpreter corruption, silent data races. SafeThreadState stores pthread_t and Gil asserts pthread_self() == pThreadState.thread. Aborts on mismatch.
MED Nested Gil acquisition (deadlock) Thread hangs in PyEval_RestoreThread. Header comment explicitly forbids nesting: "Do not nest these, as a second GIL acquire will deadlock." No enforcement — relies on caller discipline.
LOW Module leaks exception value containing sensitive data in crash dump PII/secrets visible in crash report. 719d5e1836c explicitly omits exception value from the crash dump. Only exception type and call path are included.
LOW Module name > 15 chars corrupts thread name ERANGE from OS, thread unnamed. Silently truncated with .substr(0, 15) at construction.
Known gap: There is no timeout or kill mechanism for a module whose serve() hangs. ThreadMonitor can observe high CPU but cannot forcibly terminate the module. This is a deliberate architectural gap — a cooperative shutdown model is assumed.

5. Failure Modes, Edge Cases & Blast Radius

FailureBlast RadiusObservable Signal
serve() throws → module fails Single module dark. Other modules, the mgr process, and all non-Python mgr functions continue unaffected. Cluster log error message. ceph status health warning. Crash dump. l_pym_alive perf counter = 0.
Module stuck in serve() (no return) Thread and GIL slot permanently occupied. Module-specific finisher queue grows unbounded if commands continue arriving. ThreadMonitor CPU counter elevated. No cluster log. No health check triggers automatically — requires operator polling perf dump.
shutdown() blocked (module ignoring event) mgr shutdown hangs until OS kills the process. Python GC of other modules may be deferred. mgr process does not exit gracefully. No automated watchdog.
Python GC releases GIL mid-operation If C++ caller holds a non-GIL lock and Python calls back into C++, lock-order inversion is possible. Policy documented in Gil.h: never acquire locks while holding GIL. Deadlock; no crash. Difficult to diagnose.
Perf counter null (module built without counters) No crash — both serve() and shutdown() guard with if (py_module->perfcounter). No alive counter visible in perf dump for that module.
pClassInstance is null at call time Immediate ceph_assert abort — this is a programming error, not a runtime condition. Subclass is required to populate it before invoking any of the three public methods. mgr daemon crash with assert backtrace.

6. Observability & Triage Playbook

Perf Counters (since 95a90f7da8a)

CounterWhat it tells you
mgr_module_<name>.alive 1 = serve() is running; 0 = exited (normally or via exception). Set atomically in C++ harness.
mgr_module_<name>.notify_avg_usec Latency of notify dispatches. High value = slow Python event handler.
mgr_module_<name>.cmd_avg_usec Latency of CLI command handler. High value = slow Python command handler.
mgr_module_<name>.cpu_usage CPU % from ThreadMonitor via /proc/<pid>/task/<tid>/stat.
mgr_module_<name>.mem_rss_current RSS in bytes for the mgr process (all modules share one process).

Log Signals

  • Cluster log (clog): "Unhandled exception from module '<name>' while running on mgr.<id>: <exc_type>" → module serve() crashed.
  • Local daemon log (derr): Full Python traceback with exception type and call path. No exception value (privacy).
  • Crash dump: Fields mgr_module, mgr_module_caller, mgr_python_exception, backtrace[]. Triggers cluster health warning about daemon crash.
  • Thread startup: dout(4) "Entering thread for <name>" at module thread entry.

Quick Triage Commands

# Is the module alive?
ceph daemon mgr.<id> perf dump | python3 -c \
  "import json,sys; d=json.load(sys.stdin); \
   print({k:v['alive'] for k,v in d.items() if 'alive' in v})"

# Check for module failure in MgrMap
ceph mgr module ls

# Full perf dump for one module
ceph daemon mgr.<id> perf dump mgr_module_<name>

# Check daemon log for Python traceback
grep "PyModuleRunner::serve\|handle_pyerror\|Unhandled exception" /var/log/ceph/ceph-mgr.*.log

Debugging GIL / Thread Issues

  • GIL acquire/release logged at dout level 20–25 (verbose): ceph config set mgr debug_mgr 20/25.
  • Wrong-thread GIL use: asserts immediately with pthread_self() == pThreadState.thread failure in Gil::Gil.
  • Nested GIL: deadlocks in PyEval_RestoreThread — look for a thread stack with two Gil::Gil frames.
