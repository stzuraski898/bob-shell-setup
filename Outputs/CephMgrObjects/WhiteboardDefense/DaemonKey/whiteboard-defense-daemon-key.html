1 · Architecture & Mental Model

DaemonKey is a named, typed pair that uniquely identifies one daemon instance within a Ceph cluster. It replaced raw std::pair<std::string,std::string> everywhere in the manager (5aac7eba). It carries no state beyond its two string fields and has no heap overhead beyond those strings.

Struct layout

struct DaemonKey {
    std::string type;   // "osd", "mon", "mds", "client", …
    std::string name;   // "1", "a", "admin", …
    static std::pair<DaemonKey, bool> parse(const std::string& s);
};

Canonical string form — the dot invariant

┌───────────────────────────────────────────────────────────────────┐ │ Wire format: "type.name" │ │ │ │ parse("osd.1") ──▶ DaemonKey{ type="osd", name="1" } │ │ │ │ operator<<(os, key) ──▶ os << type << '.' << name │ │ │ │ ceph::to_string(key) ──▶ type + '.' + name │ │ │ │ All three functions agree on '.' as the sole separator. │ │ No divergence exists in current HEAD or commit history. │ └───────────────────────────────────────────────────────────────────┘

Role in the manager subsystem

Ceph manager (src/mgr/) │ ├─ DaemonStateIndex — keyed by std::map<DaemonKey, …> │ uses operator< for ordering │ ├─ MgrClient / Mgr — logs, error messages, debug output │ uses operator<< to print "osd.1" (never "osd,1") │ └─ command parsing / CLI uses parse() to reconstruct a DaemonKey from a string arg

3 · Data Structures, Algorithms & Invariants

Key composition

FieldTypeMeaningExamples
typestd::stringService type — primary sort key"osd", "mon", "mds", "client"
namestd::stringService instance ID — secondary sort key"1", "a", "admin"

Ordering algorithm (operator<)

1. compare(lhs.type, rhs.type) → cmp
2. if cmp < 0: return true   (type less)
3. if cmp > 0: return false  (type greater)
4. else:       return lhs.name < rhs.name

Strict weak order ✓ — irreflexive, asymmetric, transitive. Suitable for std::map / std::set keys.

Parse algorithm

p = s.find('.')         // index of FIRST dot
if p == npos → return { {}, false }
type = s.substr(0, p)   // everything before first dot
name = s.substr(p+1)    // everything after first dot (may contain more dots)
return { DaemonKey{type, name}, true }

Round-trip property: parse(to_string(k)) == {k, true} for any key where both type and name are non-empty and type contains no dot. Established implicitly by shared dot invariant (5aac7eba).

Full invariant registry

  • I-1 A dot must be present for parse to succeed (no dot → false)
  • I-2 parse failure returns {{}, false} — never throws
  • I-3 type = s.substr(0, first_dot)
  • I-4 name = s.substr(first_dot + 1) — captures everything including any further dots
  • I-5 type is primary sort key
  • I-6 name is secondary sort key (tiebreaker only when types are equal)
  • I-7 operator< satisfies strict weak ordering
  • I-8 operator<< emits exactly type << '.' << name — no spaces, no extra chars
  • I-9 operator<< output == ceph::to_string output (must never diverge)
  • I-10 operator<< is a free function — ADL correctness requirement
  • I-11 to_string returns exactly type + '.' + name
  • I-12 to_string output == operator<< output
  • I-13 to_string is in namespace ceph — ADL correctness requirement
  • I-14 Round-trip: parse(to_string(k)).first == k and .second == true for non-empty fields

All invariants established by 5aac7eba. No invariant has been modified or reverted since.

4 · Threat Model & Adversarial Handling

Scope: DaemonKey is an internal data-structure type used within the Ceph manager process. It does not directly receive network input, authenticate callers, or hold credentials. The relevant adversarial surface is malformed / unexpected input strings fed through parse() from CLI commands, mon maps, or mgr state messages.
ScenarioInput / ActorBehaviourRiskMitigation
No dot in input "osd1", "" parse returns {{}, false}; no panic, no throw Low Caller must check the bool; if ignored, a zero-value key enters the map silently. Caller responsibility.
Empty type (".foo") — UNGROUNDED U-1 String starting with dot parse returns {DaemonKey{"","foo"}, true} — success, with empty type Medium No guard in DaemonKey. Callers that key off type would map this to an unnamed service type. Not established as valid by any commit. Callers should validate before inserting into state maps.
Empty name ("osd.") — UNGROUNDED U-1 String ending with dot parse returns {DaemonKey{"osd",""}, true} — success, with empty name Medium Same as above. Collisions possible if multiple daemons parse to the same empty-name key.
Bare dot (".") — UNGROUNDED U-1/U-2 "." parse returns {DaemonKey{"",""}, true}. Round-trip holds mechanically: to_string → ".". Medium Silently produces a zero-value key that looks valid. If inserted into DaemonStateIndex, it occupies a slot for ""/""\. No crash, but logically wrong.
Extra dots in name ("osd.1.extra") Name with embedded dots parse → {DaemonKey{"osd","1.extra"}, true} — intentional; name captures everything after first dot Low Designed behaviour (I-4). Name dots are safe. to_string / operator<< reproduce them faithfully.
Arbitrarily large strings Attacker-controlled long input std::string::find + substr — O(n) scan, then two heap allocations proportional to input length Medium No length cap inside DaemonKey. Rate-limiting and size checks must be enforced by message parsing layers upstream (mon/mgr protocol handlers), not here.
Map key collision / type confusion Two keys that differ by separator convention operator< is purely lexicographic — no normalisation. "OSD.1" ≠ "osd.1" (case-sensitive). Low Ceph daemon types are lower-case by convention. Case normalisation is the responsibility of callers / service registrations, not DaemonKey.
Ignored parse failure bool Caller neglects .second check Returns zero-value DaemonKey{"",""} with false. If caller uses .first unconditionally, a blank key enters the data store. Medium DaemonKey has no way to encode "invalid" beyond the bool. This is a caller-contract issue, not a DaemonKey bug. Migrating to std::optional<DaemonKey> would make misuse harder.

5 · Failure Modes, Edge Cases & Blast Radius

FailureTriggerBlast radiusDetectable?
Dot invariant violation A future commit changes operator<< to use ',' or '/' but does not update to_string or parse High — log output, CLI, and round-trip parsing all diverge. State lookups silently miss. tracker #42079 re-opens. Caught by any test that parses a key printed by the logger. No dedicated unit test exists in this file.
Empty-field key inserted into DaemonStateIndex parse(".foo") or parse("osd.") result not validated by caller (U-1) Medium — one spurious entry in the daemon map; potential collision if two callers produce the same empty-field key. Map remains consistent; no crash. Only via map introspection or log output printing ".foo" / "osd." — visually obvious but not asserted.
Map ordering anomaly under non-ASCII input std::string::compare is byte-order on the narrow char sequence. Non-UTF-8 / multi-byte sequences may sort differently than expected. Negligible — daemon type/name fields are ASCII identifiers in practice. Ordering is still consistent; no UB. Would only surface if non-ASCII daemon names were ever introduced.
OOM on very long key strings std::string copy / substr allocations on megabyte-scale inputs Medium — std::bad_alloc thrown by string allocator. Ceph's mgr would crash / restart. Must be prevented upstream. Not detectable inside DaemonKey; upstream message-size limits are the control.
Strict weak ordering broken Cannot happen with current implementation (analysis in §3 shows three-branch form is correct). Would require a code change. Critical — std::map/std::set UB on the daemon state index (undefined behaviour per C++ standard). Caught at compile time by -fsanitize=address,undefined or a simple ordering unit test.
ADL picks wrong operator<< Cannot happen in current code (aec62d9e header cleanup ensures <iosfwd> only); would surface if <utility> ever introduced a competing operator<< for pairs. Medium — logs would again show "osd,1" form. Regression of #42079. Visible in any log line that prints a daemon key.
