1 · High-Level Architecture & Mental Model

Role in ceph-mgr

When ceph-mgr is in standby mode (not the elected active manager), it still loads Python modules. These modules run a reduced standby persona — they can read config, fetch kv-store values, and report back the active module's URI — but they cannot drive the cluster. StandbyPyModules is the sole lifecycle manager for this standby Python layer.

ceph-mgr (standby daemon) │ ├─ PyModuleRegistry (module catalogue + PyModuleConfig owner) │ │ shared ref ──────────────────────────────────────────┐ │ │ │ └─ StandbyPyModules ─── StandbyPyModuleState ──────────────────┤ │ ├─ MgrMap (guarded by state::lock) │ │ ├─ PyModuleConfig & ─────────────────┘ (lifetime: registry) │ └─ MonClient & (self-locking, handed out freely) │ ├─ [map] modules: name → StandbyPyModule* │ │ │ └─ StandbyPyModule (extends PyModuleRunner) │ ├─ load() – constructs Python standby class instance │ ├─ serve() thread – runs Python serve() loop │ ├─ get_config() – reads in-memory PyModuleConfig (fast) │ ├─ get_store() – synchronous mon "config-key get" command │ └─ get_active_uri() – reads MgrMap::services under lock │ └─ Finisher & – module loads dispatched here (avoids lock cycles)

Start-up Flow

Caller (MgrStandby) │ ├─ construct StandbyPyModules(mgr_map, module_config, clog, monc, finisher) │ └─ state.set_mgr_map(mgr_map) ← MUST happen before any start_one │ └─ for each module: start_one(py_module) │ ├─ [under lock] allocate raw StandbyPyModule* (NOT yet in map) │ └─ finisher.queue(lambda) │ ├─ standby_module->load() ← GIL acquired with new-thread-state │ ├─ success: [under lock] modules.emplace(name, ptr) │ │ thread.create("mgr.<name>") │ └─ failure: delete ptr (logged to derr + crash dump) └─

Shutdown / Promotion Teardown Ordering

[caller stops Finisher first — undocumented but required precondition] │ StandbyPyModules::shutdown() ├─ [acquire lock] ├─ for each module: │ unlock → module->shutdown() ← Python shutdown() call (blocks) │ lock ├─ for each module: │ unlock → module->thread.join() │ lock └─ modules.clear() ← under lock, last
⚠ The Finisher must be stopped before shutdown() is called. If it isn't, the lambda in flight can insert into modules while the shutdown loop iterates with lock dropped, invalidating the iterator. This precondition is implicit — no assert, no comment establishes it in code.

2 · Architectural Decisions & Trade-offs

Decision (Why X?)Alternative (Why Not Y?)Rationale & Commit
No local config cache — standby reads shared PyModuleConfig& owned by the registry Original design (c1471c75) had a LoadConfigThread that populated a local config_cache; with_config blocked on a Cond until loaded 3193d40d eliminated the thread and local copy. Config is now a shared reference. Eliminates a whole threading surface (the Cond wait, the race on shutdown) at the cost of: if config isn't ready yet, get_config silently returns false rather than blocking.
Module loads dispatched to a Finisher — start_one queues a lambda and returns immediately Previous design called module->load() synchronously while holding lock f22347db (tracker#37997): synchronous load + lock held = potential lock cycle with Python GIL acquisition. Finisher breaks the cycle.
Module NOT registered in map until after successful load f22347db registered the module before queuing to the Finisher 56e34f58 (tracker#41736): a notify arriving between pre-registration and actual load would call into an uninitialized Python object. Fix: raw-allocate outside, emplace only on success.
get_store is synchronous (blocking mon command) Active modules maintain an in-memory write-through cache of kv-store values 6185bd66 inline comment: "acceptable cost because standby modules should not be doing a lot." Caching would require invalidation signals that standbys don't receive.
MonClient& handed out directly — no lock wrapper around get_monc() Could gate access through StandbyPyModuleState::lock 6185bd66 comment: "MonClient does all its own locking so we're happy to hand out references."
GIL acquired with true (new-thread-state) in load() Original c1471c75 used Gil(pMyThreadState) without true 29193a47: load() is called from the Finisher OS thread, not a Python-created thread. true tells the GIL wrapper to create a new Python thread state for this OS thread.
Config key prefix is literal "mgr/" Earlier versions used PyModuleRegistry::config_prefix, then PyModule::config_prefix b0a4bff8: those symbols are for kv-store key names; this code reads config option names. The namespace is different. Bug fix, not a preference.
KV store key prefix uses PyModule::mgr_store_prefix Originally used PyModule::config_prefix 3bafb5e5: rename to clarify the distinction. Config options ≠ kv-store keys.
shutdown unlocks around each module->shutdown() call Hold lock throughout shutdown c1471c75: Python shutdown() may call back into get_config/get_active_uri, which acquire StandbyPyModuleState::lock. Holding the outer lock during Python calls = deadlock.

StandbyPyModules private
  • A name appears in the map only after successful load() — established 56e34f58
  • All access guarded by StandbyPyModules::lock
  • ceph_assert(em.second) guards against duplicate insertion (fires in Finisher lambda)
StandbyPyModuleState::mgr_map MgrMap value copy
  • Assigned at construction (before any start_one) and on every handle_mgr_map call
  • All reads via with_mgr_map which holds state::lock
StandbyPyModuleState::module_config PyModuleConfig& reference
  • Lifetime of pointed-to object must exceed StandbyPyModuleState
  • All reads via with_config which holds state::lock
  • No blocking wait — if config not yet populated, get_config silently returns false
StandbyPyModuleState::lock ceph::mutex mutable Protects mgr_map; provides read-lock for module_config ref. Callbacks passed to with_config / with_mgr_map must not re-acquire this lock (no re-entrancy).
StandbyPyModules::lock ceph::mutex mutable Protects modules map. Must not be held across blocking calls (Python GIL, mon commands).
pClassInstance PyObject* in StandbyPyModule
  • nullptr until load() succeeds
  • Python standby class constructor receives (pThisPtr, pModuleName) as args
  • Py_XDECREF'd in destructor under GIL
Finisher& Reference, lifetime: caller
  • Must be running before start_one is called — f22347db
  • Must be stopped before shutdown() is called — undocumented precondition

4 · Threat Model & Adversarial Handling

Actor / ScenarioAttack SurfaceActual BehaviourSeverity
Malicious Python module raises exception in serve() PyModuleRunner::serve() Exception caught, logged to cluster log (f4763c32). Crash dump generated with module name + caller (719d5e18). Thread exits cleanly; other modules unaffected. Contained
Malicious Python module raises exception in load() StandbyPyModule::load() — PyObject_CallObject pClassInstance stays nullptr. handle_pyerror(true, name, "StandbyPyModule::load") generates crash dump. Module deleted, never inserted into map. Other modules proceed. Contained
Malicious Python module calls get_store with a key containing " or \ get_store() — JSON built by ostringstream string concatenation JSON sent to mon is malformed. Mon likely rejects it; r != 0 logged + returns false. No crash. But the key content is operator-controlled (module names come from the module registry), so exploitation requires operator-level access in practice. Latent/Low
Duplicate start_one call for same module name start_one() — Finisher lambda f22347db outer-scope ceph_assert(count==0) was removed by 56e34f58. Only guard is ceph_assert(em.second) inside the lambda. A duplicate fires this assert → daemon aborts. Requires caller to send duplicate names, which no caller currently does. Abort
Notify/callback delivered during module load window Race between Finisher lambda and incoming notify Fixed by 56e34f58: module not in map until post-load emplace. A notify cannot reach a half-initialized module. Fixed
Finisher stopped/destroyed while load lambdas are in-flight start_one() raw pointer + this capture The StandbyPyModule* leaks; the this capture becomes a use-after-free if StandbyPyModules is destroyed first. No RAII wrapper, no ownership transfer. In practice the caller controls Finisher + object lifetimes and ensures correct ordering, but this is undocumented. UAF/Leak if misused
Mon unavailable or disconnected during get_store C_SaferCond::wait() in get_store No timeout. Blocks indefinitely. If this happens during daemon shutdown, the shutdown thread hangs. The inline comment acknowledges the synchronous cost but not the shutdown-interruptibility gap. Hang
Python module calls get_config before registry populates PyModuleConfig with_config — no blocking wait since 3193d40d Original design (c1471c75) blocked on a Cond. After 3193d40d, returns empty config silently (false). Module sees no config — not a crash, but a silent miss that may cause incorrect behaviour. Silent Miss

5 · Failure Modes, Edge Cases & Blast Radius

FailureTriggerBlast RadiusRecovery
Module load() fails Python exception in module class constructor Single module silently absent from modules map. Logged to derr + crash dump. Other modules unaffected. Module excluded from map. No retry. Restarting the mgr daemon reloads it.
shutdown() hangs on module->shutdown() Python shutdown() hangs (infinite loop, deadlock, blocking I/O) Entire standby daemon stuck at shutdown. No timeout, no kill signal. Noted as known limitation since c1471c75 (FIXME: "completely identical to ActivePyModules"). External SIGKILL only.
get_store hangs during shutdown Mon unreachable while Python module's serve() calls get_store() C_SaferCond::wait() never returns. Thread that called serve() blocks indefinitely. External SIGKILL only. No timeout path exists.
Finisher not stopped before shutdown() Caller ordering error Finisher lambda inserts into modules during shutdown's unlock gaps → iterator invalidation → UB / crash. Implicit caller contract. No in-code guard.
PyModuleConfig or MonClient object outlived by StandbyPyModules Caller destroys registry/monc before standby modules Dangling reference dereference. All config/store reads become UB. Lifetime invariant entirely on the caller — no assertion in code.
Thread naming bug (original) Thread name built from local ostringstream whose lifetime ended Thread name garbage / crash in thread-naming code Fixed bb4e71ed: now passes module->get_name().c_str() (valid for module lifetime).
Config prefix wrong (historical) get_config used PyModule::config_prefix (kv-store namespace) All standby config reads returned false (wrong key namespace) Fixed b0a4bff8: literal "mgr/".
Notify to half-initialized module (historical) Module inserted pre-load in f22347db Notify dispatched to pClassInstance == nullptr → crash Fixed 56e34f58: map insert deferred until post-load success.
