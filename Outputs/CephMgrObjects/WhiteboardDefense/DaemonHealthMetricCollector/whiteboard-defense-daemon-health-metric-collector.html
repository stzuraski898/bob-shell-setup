1. High-Level Architecture & Mental Model

DaemonHealthMetricCollector is the Ceph Manager (ceph-mgr) aggregation component that folds per-daemon incoming telemetry metrics (received from OSDs, MDSs, and other daemons via MMgrReport) into cluster-wide Ceph health alerts stored in health_check_map_t.

It encapsulates polymorphic accumulation and summary generation behind an abstract base class, hiding concrete metric logic in the anonymous namespace of DaemonHealthMetricCollector.cc.

|                                                                                                    |
|  [OSD / MDS Daemon] --(MMgrReport with DaemonHealthMetric)--> [DaemonServer / MgrClusterState]     |
+----------------------------------------------------------------------------------------------------+
                                               |
                                               v
+----------------------------------------------------------------------------------------------------+
|                         COLLECTION CYCLE: DaemonHealthMetricCollector Base                         |
|                                                                                                    |
|  1. Instantiate via Factory:                                                                       |

|         ├─► reported == false? ────────────► [No-Op; no entry created in health_check_map]         |
|         │                                                                                          |
|         └─► reported == true:                                                                      |
|                 health_check_t& check = _get_check(cm);                                            |
|                 _summarize(check);                                                                 |
+----------------------------------------------------------------------------------------------------+
                                               |
                                               v
+----------------------------------------------------------------------------------------------------+
|                                   CLUSTER HEALTH ALERT DISPATCH                                    |
|                                                                                                    |
|   ├── SlowOps   ──► Summary: "N slow ops, oldest one blocked for M sec, [daemons...]"              |
|   │                 Count: 1, Severity: HEALTH_WARN, Detail: (empty - embedded in summary)          |

Key Architectural Mental Model:
Collectors are ephemeral per-summary aggregators. An instance is constructed for a specific metric collection pass across active daemons, updated with each daemon's metrics, flushed once via summarize() into the manager's health map, and destroyed.

3. Data Structures, Algorithms & Invariants

Internal Data Structures

  • daemon_metric_t value: Dual-purpose 64-bit union / struct accumulator.
    • SlowOps: value.n1 = Total slow ops (sum), value.n2 = Oldest blocked duration in seconds (running std::max).
    • PendingPGs: value.n = Total pending creation PGs (sum via metric.get_n()).
  • bool reported = false: One-way latch protecting against health alert clearing.
  • std::vector<DaemonKey> daemons / osds: Dynamic list of reporting daemons that reported non-zero metric values during the current cycle.

Core Invariants

Invariant 1: Monotonic Alert Latch (Tracker #41741)

reported is monotonically non-decreasing over the lifetime of a collector instance: false -> true is irreversible. summarize() will fire if and only if at least one daemon reported non-zero metrics.

Invariant 2: Extreme-Value Duration Tracking

For SlowOps, value.n2 = std::max(value.n2, blocked_time) ensures the cluster health summary highlights the worst-case blocked request latency across the entire cluster, rather than an uninformative mean or additive sum.

Invariant 3: Zero-Metric Filter

Daemons reporting zero slow ops or zero pending PGs execute the unconditional accumulator (value += 0) but are not appended to the daemons / osds vector and return false from _update().

Invariant 4: Formatting Separation (Summary vs. Detail)

SlowOps: Populates check.summary with daemon names (capped at 10) and leaves check.detail empty (// No detail).
PendingPGs: Populates check.summary with total PG count and appends the full daemon list to check.detail.

Blast Radius Analysis

  • Failure Domain: Isolated entirely to the Ceph Manager health check reporting subsystem (ceph-mgr).
  • Data Plane Impact: Zero. A crash or error in metric aggregation cannot corrupt user data, stall PG peering, or disrupt client I/O.
  • Control Plane Impact: If DaemonHealthMetricCollector throws or aborts, ceph-mgr restarts, triggering standby mgr failover. Health alerts will momentarily show stale state until the new active mgr receives fresh MMgrReport frames.

6. Observability & Triage Playbook

How to Observe Collector State

  • CLI Inspection: ceph health detail or ceph status 
    HEALTH_WARN 153 slow ops, oldest one blocked for 38 sec, daemons [osd.3,osd.4,osd.5] have slow ops.
HEALTH_WARN 12 PGs pending on creation
  • Prometheus Metric Scrape: Scraped by mgr/prometheus via the health check map.
  • Mgr Debug Logging: Set ceph config set mgr debug_mgr 20 to trace daemon metric reports received over MMgrReport.

Operator Triage Playbook

Step 1: Identify Offending Daemons

Check ceph health detail. For SLOW_OPS, look at the daemon list in the summary string (e.g. [osd.12,osd.45]). For PENDING_CREATING_PGS, inspect the detail lines.

Step 2: Check OSD Disk / Network Latency

Connect to the flagged OSD hosts and run ceph daemon osd.<id> ops or check underlying disk saturation via iostat -xz 1 to determine if slow ops stem from hardware stalls or network dropped packets.

Step 3: Verify Metric Clearing

Once the underlying disk or peering stall clears, the next incoming MMgrReport will contain zero slow ops, and the new collector pass will not set reported, automatically resolving the health check.
