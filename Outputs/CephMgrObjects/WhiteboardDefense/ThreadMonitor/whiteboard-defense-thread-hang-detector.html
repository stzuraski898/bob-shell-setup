§1 High-Level Architecture & Mental Model

Purpose: A background polling thread that reads per-thread CPU ticks from /proc/self/task/<tid>/stat and process-wide RSS from /proc/self/statm, then writes the computed values into each registered PyModule's PerfCounters. It exposes per-module CPU % and memory RSS via ceph daemon mgr.<id> perf dump without modifying the modules themselves. (95a90f7d)

⚠ RSS and CPU are not atomically consistent
RSS is written in Phase 1 and CPU in Phase 3. They are from different wall-clock moments within the same iteration. A perf dump snapshot may show an RSS from T+0 paired with a CPU from T+0.5 ms. No commit establishes this as intentional.

§2 Architectural Decisions & Trade-offs

DecisionWhy this, not thatTrade-off / riskCommit
Three-phase lock split
lock → copy → unlock → I/O → lock → write		 Avoid holding monitored_threads_mutex during /proc file I/O (unbounded latency). Lets register_thread and the loop coexist without long lock contention. RSS and CPU values in a single iteration come from different points in time. A thread that deregisters between phases is silently skipped in Phase 3 (correct, but stale data in the result vector). 95a90f7d
Single polling thread, no thread pool mgr modules are O(10), not O(1000). A single background thread with sequential /proc reads is sufficient; no scheduling complexity. If many modules are registered, Phase 2 becomes O(N × file I/O). No per-thread parallelism. Latency of one full iteration can exceed monitoring_interval under contention. 95a90f7d
md_config_obs_t observer for hot reload Allows mgr_module_monitor_interval changes at runtime via ceph config set mgr without a restart. Zero interval stops monitoring entirely. monitoring_interval is written in handle_conf_change and read in monitoring_loop without a lock. On 64-bit Linux this 64-bit value is likely hardware-atomic, but no formal std::atomic or memory order is established. 95a90f7d
Process-wide RSS (not per-thread) Linux does not expose per-thread RSS. /proc/self/statm gives the only available resident-set count. Same value is broadcast to every registered module's counter. All modules see the same RSS — there is no per-module memory isolation in the counter. The counter is process-wide posing as per-module. 95a90f7d
Separate serve-thread tracking Ceph mgr Python modules run a main thread and an optional serve thread. Each is tracked independently under the same MonitoredThreadInfo. Serve thread death clears serve_thread_id = 0 but keeps the main entry. If the serve TID is recycled by a new unrelated thread between loop iterations, the reused TID will be read and produce a garbage CPU spike (negative delta possible, no TID-reuse guard). 95a90f7d
Dead-thread detection via /proc open failure A thread that has exited causes /proc/self/task/<tid>/stat to disappear. read_thread_stat returning false is treated as thread death → entry erased. File-open failure ≠ thread death; it can also mean temporary kernel pressure or a permissions change. Entry is permanently removed on the first failure. No retry. Erased entries are logged at dout(0). 95a90f7d
Sysconf values cached at construction sysconf(_SC_CLK_TCK) and sysconf(_SC_PAGESIZE) are system-wide constants that never change during a process lifetime. Caching avoids syscall overhead on every loop iteration. If sysconf returns -1 (error), the values are stored as -1. The constructor does not propagate this failure. The loop guard at cc:79 catches it but has the std::terminate() bug (§5). 95a90f7d
Interval bug fix: raw int64_t → chrono::seconds Original code assigned raw int64_t seconds directly to a ceph::mono_clock::duration (nanosecond resolution). A config value of 2 produced a 2 ns interval → effectively a busy-spin. Fixed by wrapping with std::chrono::seconds(). Fix applied only to the constructor initialiser. handle_conf_change already wrapped with std::chrono::seconds() from day one, so runtime changes were always correct. 28647966 (Fixes: #76938)
Sleep added on read_process_statm failure Original code had a bare continue after the statm read failure — no sleep → tight CPU spin. Fix adds sleep_for(monitoring_interval) before continue. Same commit as interval fix. The retry loop still does not check running before sleeping; shutdown latency can be up to monitoring_interval on this path too. 28647966 (Fixes: #76938)

§3 Data Structures, Algorithms & Invariants

Core map: monitored_threads

Type: std::map<pid_t, MonitoredThreadInfo>
Lock: std::mutex monitored_threads_mutex
Access pattern: read+write in Phase 1 & 3 (loop), write in register_thread

  • Key = Linux TID (pid_t)
  • Ordered map — insertion order irrelevant; O(log N) lookup in Phase 3
  • No deregister API — entries removed only when read_thread_stat fails (thread exit)
  • Duplicate registration silently rejected (count(thread_id) guard)

ThreadSnapshot struct

Stored per-thread (main + serve) as last_snapshot / last_serve_snapshot.

FieldTypeDefaultMeaning
utimelong long0User-mode ticks at last sample

⚠ utime/stime default to 0 at registration. First CPU sample = Δ from thread birth, not registration. Inflated first reading. (95a90f7d, ungrounded)

CPU Percentage Formula

cpu_pct = (Δutime + Δstime) / (m_clock_ticks_per_sec × Δwall_seconds) × 100.0 where: Δutime = new_utime - last_snapshot.utime ← jiffies (user mode) Δstime = new_stime - last_snapshot.stime ← jiffies (kernel mode) Δwall = chrono::duration<double>(new_ts - last_snapshot.timestamp) CLK_TCK = sysconf(_SC_CLK_TCK) ← typically 100 Hz on Linux Guards: elapsed_seconds ≤ 0 → return 0.0 ← division-by-zero guard Δjiffies < 0 → negative result (no clamp) ← TID reuse hazard result > 100% → possible on multi-core ← no cap cpu_pct cast to uint64_t before perfcounter.set() ← truncates fraction, wraps on negative

/proc parsing: read_thread_stat

/proc/self/task/<tid>/stat format (proc(5)): pid (comm) state ppid pgrp session tty_nr tpgid flags minflt cminflt majflt cmajflt utime stime ... └──┘ parenthesised, may contain spaces and '('/')' — skip by finding last ')' Strategy: 1. rfind(')') → end 2. substr(end + 2) → remainder (skips ") ") 3. skip 11 fields: state ppid pgrp session tty_nr tpgid flags minflt cminflt majflt cmajflt 4. ss >> utime >> stime ⚠ Step 4 has no success check — if stream fails, utime/stime hold garbage, returns true

§4 Threat Model & Adversarial Handling

Actor / ScenarioWhat happensImpactMitigation
Rogue module calls register_thread with a foreign TID
(e.g., TID of a system thread it doesn't own)		 No ownership check. The TID is accepted and polled. If the file exists, CPU data for that foreign thread is written to this module's perf counter. No authentication on TID ownership. Medium CPU stats misattributed; no privilege escalation. All actors run inside the mgr process with the same UID. None in code. Mitigated by the fact that only trusted mgr-internal code calls register_thread (not Python-level API).
Module passes a recycled TID
(old thread exited, OS reused TID for an unrelated thread)		 New thread's CPU ticks are read. Since the snapshot has the old thread's tick baseline, Δjiffies may be huge (positive spike) or negative (new thread has lower ticks). calculate_cpu_percentage produces inflated or negative values. Negative result is cast to uint64_t → wrap-around to very large integer written to perfcounter. Medium Bogus perf counter value; no crash, no privilege issue. Misleading observability data. None. No TID reuse detection exists. No clamp or sign check in calculate_cpu_percentage.
Module registers same TID twice Duplicate guard in register_thread: monitored_threads.count(thread_id) → early return with dout(20). Second registration is silently rejected. None Idempotent. No overwrite, no crash. Guard at cc:47–50. (95a90f7d)
Module deregisters / exits while loop is in Phase 2 No deregister API exists. If a module exits, its PyModuleRef may be released. Phase 3 checks py_module && py_module->perfcounter before writing. However, the PyModuleRef (shared_ptr) in the map still holds a reference, so the object is not destroyed while the entry exists. Low shared_ptr ownership prevents use-after-free during loop. Entry persists until /proc stat read fails (thread exit). Copy-by-value into ThreadEntry in Phase 1 retains the shared_ptr. Entry erase in Phase 3 only after main_ok == false.
/proc/self/statm returns a truncated / corrupt line statm_file >> vsize_pages >> rss_pages — no success check. If extraction fails, rss_pages retains its pre-call value (0 on the first call, or the previous iteration's value if declared differently). Function returns true. Caller writes rss_bytes = 0 to all module perf counters silently. Medium Silent false RSS readings. No error log on this path. None currently. Should check statm_file.fail().
Config change fires mgr_module_monitor_interval = 0 handle_conf_change calls stop_monitoring(). Atomic exchange sets running=false. Loop exits after current sleep_for completes (up to full interval latency). Monitoring halts cleanly. Intended By design. (95a90f7d)
Config change fires while loop is sleeping
(interval changed to shorter value)		 New monitoring_interval value written (no lock). Loop is already sleeping for the old interval. New interval only takes effect after the current sleep expires. No wake-up mechanism. Cosmetic Delayed propagation of up to one old interval. Expected, but undocumented. No condition_variable wakeup. Acknowledged latency.

§5 Failure Modes, Edge Cases & Blast Radius

🔴 CRITICAL — std::terminate() on sysconf failure (DIVERGED, 95a90f7d)

If sysconf(_SC_CLK_TCK) or sysconf(_SC_PAGESIZE) returns -1 (error), monitoring_loop at cc:82 sets running = false internally and returns. This causes stop_monitoring() (called by ~ThreadMonitor) to short-circuit via if (!running.exchange(false)) { return; } — it never reaches the join(). The unique_ptr<std::thread> destructor then calls std::thread::~thread() on a still-joinable thread → std::terminate() → process crash.

The joinable() guard in stop_monitoring() at cc:35 is unreachable on this code path and gives false safety. Sysconf failure is extremely unlikely on Linux but this is a correctness defect.

Fix: monitoring_loop should not set running=false; instead exit silently and let stop_monitoring's join handle cleanup. Or: have the loop set a separate error flag without touching running.

🔴 DIVERGED — read_thread_stat returns true with garbage utime/stime (95a90f7d)

ss >> utime >> stime at cc:226 has no stream failure check. If the stream is in a fail state (truncated line, bad offset), the function returns true with uninitialised long long values. process_thread_stats calls calculate_cpu_percentage with those values → undefined behaviour (reading uninitialised long long).

🟡 DIVERGED — read_process_statm silently reports RSS = 0 on parse failure (95a90f7d)

statm_file >> vsize_pages >> rss_pages at cc:240 has no success check. Parse failure leaves rss_pages = 0 (caller-initialised). Function returns true. All modules get mem_rss_current = 0 silently.

Triage: high cpu_usage counter on a module

  1. Check if reading is on the very first sample (first iteration after registration) — inflated by design. Wait one more interval.
  2. Check ceph config get mgr mgr_module_monitor_interval — ensure it's a reasonable integer (e.g., 5). If it was recently changed from 0, the first sample after restart may be inflated.
  3. Correlate with actual system CPU (top -H -p <mgr-pid>). If system CPU is low but counter is high: likely TID reuse producing negative→wrap or a first-sample spike.
  4. Check for dout(0) "Registered thread" or "Removing dead thread" messages in mgr log around the same time.

Triage: all modules show RSS = 0

  1. Check for derr "Failed to read process memory info" in mgr log.
  2. Verify /proc/self/statm is readable from inside the mgr process container/namespace.
  3. If no derr but RSS still 0: likely silent parse failure in read_process_statm (stream extraction succeeded but returned 0 — check actual file contents with cat /proc/<mgr-pid>/statm).

Triage: MGR process crashing with std::terminate() at shutdown

  1. Check for derr "Failed to retrieve system configuration" — this would be the sysconf failure path.
  2. The std::terminate() will produce a core dump. Backtrace will show std::thread::~thread() called on a joinable thread from ThreadMonitor::~ThreadMonitor().
  3. Workaround: set mgr_module_monitor_interval = 0 before shutdown to stop the monitor thread via handle_conf_change before the destructor runs.
