1 · High-Level Architecture & Mental Model

DaemonHealthMetric is a lightweight, serialisable value-type that carries a single typed health counter from a daemon (OSD or MON) to the Ceph manager (mgr). It is a one-way message payload: daemons construct instances, serialise them over the Ceph messenger wire protocol using DENC, and the mgr deserialises and consumes them for health checks and Prometheus exposition. 

  OSD / MON                         MGR
  ─────────                         ───
  DaemonHealthMetric(SLOW_OPS, n)   ◄── constructed by daemon
         │
         │  DENC encode  (uint8 type | uint64 n)
         ▼
  ════ Ceph messenger wire ════════════════════════════════════
         │
         ▼
  DENC decode → DaemonHealthMetric
         │
         ├──► health check aggregation  (get_type(), get_n())
         │
         ├──► Prometheus exposition     (get_type_name(), get_n())   ← 5a2b7c25
         │
         ├──► debug log                 (operator<<)                 ← adc480e3
         │
         └──► ceph-dencoder             (dump(), generate_test_instances()) ← 899276a5

Key Design Decisions at a Glance

  • Value type, not pointer type — trivially copyable, stack-allocatable, stored in vectors/lists by value.
  • Union payload — one uint64_t n field that aliases two uint32_t sub-fields (n1, n2), serialised always as the single uint64_t.
  • Enum tag + union value — the daemon_metric tag tells the consumer which interpretation applies; no polymorphism, no vtable.
  • Schema version frozen — DENC_START(1, 1, p): both v and compat pinned to 1, no migration path ever added.

3 · Data Structures, Algorithms & Invariants

3.1 · enum class daemon_metric : uint8_t

EnumeratorValue (implicit)Payload semanticsEstablished
SLOW_OPS0Single counter: slow-op count → use get_n()f4b74125
PENDING_CREATING_PGS1Pair: PGs waiting (n1) + total (n2) → use get_n1(), get_n2()f4b74125
NONE2Default/unset — no value access expectedf4b74125
Invariant (unwritten but implicit): The caller is responsible for matching the correct accessor to the metric type. SLOW_OPS → get_n() only; PENDING_CREATING_PGS → get_n1() + get_n2(). There is no enforcement in the class — any accessor can be called on any type. (UNGROUNDED finding U1.)

3.2 · union daemon_metric_t

union daemon_metric_t {
  struct {
    uint32_t n1;   // low word  — "count A" or low-32 of scalar
    uint32_t n2;   // high word — "count B" or high-32 of scalar (usually 0)
  };
  uint64_t n;      // full 64-bit view — DENC always serialises this field

  daemon_metric_t(uint32_t x, uint32_t y) : n1(x), n2(y) {}   // pair path
  daemon_metric_t(uint64_t x = 0)         : n(x) {}            // scalar path
};
  • On little-endian: n1 occupies the low 32 bits of n; n2 occupies the high 32 bits.
  • No endianness annotation exists. The DENC macro for uint64_t handles byte-swap on encode/decode, so the on-wire bytes are correct, but if code ever reads n1/n2 from a value decoded via the n path on a big-endian platform, the halves would be swapped.
  • Ceph targets are predominantly x86 little-endian; no big-endian CI is known for this path.

3.4 · DENC Wire Format

DENC_START(1, 1, p)          // version=1, compat=1 — frozen since f4b74125
  denc(v.type,    p);         // uint8_t  — enum value (0, 1, or 2)
  denc(v.value.n, p);         // uint64_t — always the full union field
DENC_FINISH(p)

On-wire size (typical): 1 header byte (DENC overhead) + 1 (type) + 8 (n) = ~10 bytes
Schema freeze: compat == 1 means any schema change requires a coordinated cluster upgrade. No migration path has ever been added in 8 years. Adding a field would require bumping both v and compat, and all decoders must understand the new version before any encoder can use it.

3.6 · dump() Output Schema (dencoder contract)

{ "type": "<string>",  // daemon_metric_name() result: "SLOW_OPS" | "PENDING_CREATING_PGS" | "NONE"
  "n":    <int64>,     // full 64-bit union view
  "n1":   <int32>,     // low 32 bits
  "n2":   <int32> }    // high 32 bits
Semantic ambiguity (U3): For SLOW_OPS, the meaningful field is "n"; "n1" and "n2" are low/high halves of the slow-op count (e.g. n=42, n1=42, n2=0). For PENDING_CREATING_PGS, the meaningful fields are "n1" and "n2"; "n" is their combined 64-bit view. No commit has type-gated the output. Log scrapers and consumers must know which fields to read per metric type.

6 · Observability & Triage Playbook

What does it look like in logs?

// operator<< output (established adc480e3):
SLOW_OPS(42|(42,0))
PENDING_CREATING_PGS(8589934593|(1,2))   // n = (2 << 32) | 1

// "???" in a log line means:
//   daemon_metric byte had an out-of-range value (post-decode corruption or future unknown type)

What does it look like in Prometheus?

  • Metric label uses get_type_name() → "SLOW_OPS" or "PENDING_CREATING_PGS" (added 5a2b7c25).
  • Value exposed via get_n() — for PENDING_CREATING_PGS this is the combined 64-bit value, not the intended individual pair counts.
  • If the Prometheus exporter emits ??? as a label, an unknown metric type was decoded.

What does it look like in ceph-dencoder?

# Encode a test instance, decode it, verify:
ceph-dencoder type DaemonHealthMetric encode decode dump_json

# Expected output:
{ "type": "SLOW_OPS", "n": 1, "n1": 1, "n2": 0 }
{ "type": "PENDING_CREATING_PGS", "n": 8589934593, "n1": 1, "n2": 2 }

Triage: "health metric shows wrong value"

  1. Check get_type() first — if it returns NONE (2), value is uninitialised (U2). Trace call site to find a default-constructed metric that leaked out.
  2. For SLOW_OPS: read get_n() — that is the authoritative count. Ignore n1/n2 in Formatter output.
  3. For PENDING_CREATING_PGS: read get_n1() (PGs waiting) and get_n2() (total). Ignore n in Formatter output.
  4. If metric type is "???" in logs/Prometheus: the type byte decoded to an out-of-range value. Check OSD version vs MGR version — potential new enumerator not known to this MGR.
  5. If DENC decode fails entirely: DENC schema version mismatch. Check that OSD and MGR are on compatible versions (schema v1 is the only version ever shipped — any deviation is a build error).

Triage: "generate_test_instances() crash / leak"

  • Pre-ed6b7124: callers received raw T* and had to delete them; ASan leaks were routine.
  • Post-ed6b7124: returns std::list<DaemonHealthMetric> by value — no heap allocation, no ownership issue. If you're on a branch still showing leaks, check if ed6b7124 was merged.
